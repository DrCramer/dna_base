# Удобные объёмы воды при разведении ДНК

Режим включается явно в `Протоколы -> Создать -> Разведения`. По умолчанию
`optimize_water_volumes = false`; старые snapshots сохраняют прежние объёмы.

## Математика и ограничения

Для одного этапа:

```text
Cfinal = C0 * D / (D + W)
error_percent = 100 * (Cfinal / Ct - 1)
```

Для двух этапов:

```text
C1 = C0 * D1 / (D1 + W1)
Cfinal = C1 * D2 / (D2 + W2)
```

Допуск проверяется по конечной концентрации каждого объекта. После выбора W1
допустимые W2 вычисляются заново от фактической C1. Проценты ошибок отдельных
этапов не складываются и не заменяют проверку конечной концентрации.

Концентрация C0 поступает из текущего resolver `RealtimeDetail.small_quantity`.
Long Quantity и Y Quantity не подставляются. Строки без Small и строки без
необходимого разведения не оптимизируются.

Оптимизатор меняет только воду. Объёмы ДНК уже определены существующим
`calculate_dilution()`, включая явно включённый минимум 15 мкл. Проверяются:

- диапазоны и дискретность воды и ДНК, если они заданы;
- минимум смеси для каждого этапа, только если соответствующий режим включён;
- доступный исходный материал для I этапа (`source_available_volume`, по умолчанию 50 мкл);
- наличие продукта I этапа для забора D2 и `first_dilution_reserve_ul`.

Лимит исходной ДНК не применяется к продукту I разведения. Если оборудование не
поддерживает рассчитанный объём, автоматического деления на порции или
самовольной смены объёма ДНК нет: строка требует решения сотрудника.

## Выбор общего плана

`protocol_dilution_optimizer.py` выполняет вторую фазу после базового расчёта.
Для одной строки используется не более 32 вариантов, для пары шагов — не более
64. Кандидаты включают предпочтительный шаг воды, допустимый baseline и общие
объёмы других объектов. Для исправления baseline вне допуска рассматриваются
ближайшие значения измерительной дискретности при неизменной ДНК.

Приоритет `fewest_volumes` использует детерминированную greedy set-cover
эвристику. Она выбирает общие объёмы, покрывающие больше строк на одну новую
настройку, затем уменьшает суммарную абсолютную ошибку. Итог сравнивается с
допустимым базовым планом. Это ограниченный по сложности поиск, а не обещание
глобально оптимального решения. Приоритет `minimum_error` сначала минимизирует
отклонение каждой строки.

Кандидаты вверх и вниз допустимы только после прямой проверки Cfinal. Объём вне
предпочтительного шага может остаться для соблюдения допуска или объединения
группы; это объясняется в примечании строки. Рабочие шаги повторно проверяются
после назначения. Неуспешный baseline сохраняется с `blocked / needs_review`,
а не объявляется готовым расчётом.

Фаза оптимизации выполняется через `asyncio.to_thread`, чтобы большие списки
не удерживали цикл обработки остальных HTTP-запросов. На синтетическом наборе
из 2000 объектов локальная проверка заняла около 5.7 с: 215 объёмов до -> 41 после,
1886 изменённых строк, 106 без изменения и 8 требующих проверки. Максимальное
отклонение готовых строк составило около 4.76% при настройке 5%. Это пример
производительности и проверки математики, не лабораторная валидация.

## Snapshot и представления

В `snapshot.dilution_settings` сохраняются допуск, шаг, приоритет, ограничения
дозирования, резерв и настройка минимума смеси. Возможны отдельные
`max_under_target_pct` / `max_over_target_pct`; по умолчанию применяется
симметричный допуск.

Каждая активная строка сохраняет `baseline_steps`, рабочие `steps` и
`optimization`: фактическую концентрацию, знаковое отклонение, результат
проверки baseline, статус, причину и остаток I разведения. В
`snapshot.dilution_optimization` сохраняются вычисленные счётчики и группы.
Миграция базы для этих JSON-полей не нужна.

Общий счётчик вариантов H2O учитывает все показанные активные строки, включая
сохранённые baseline требующих проверки. Максимальное отклонение также
показывает такие строки: большое значение не скрывается средним или максимумом
только среди готовых. Группы I и II этапов разделены; каждая содержит object_id,
плашку, лунку и признак `needs_review`.

Сортировка H2O меняет только рабочий порядок строк, а не PCR layout. Сохранённый
протокол открывается из snapshot без повторного запуска оптимизатора.

- Экран показывает рабочую воду; tooltip содержит baseline, факт и ошибку.
- Сворачиваемые блоки показывают настройки, ограничения, группы и аудит.
- Печать использует те же `steps`; флажок `Разведения` позволяет напечатать
  таблицу отдельно от этапов. Аудит округления остаётся на экране и в Excel,
  но не добавляется в печатный документ. Чередование белых и серых строк
  сохраняется в печати, включая отключённую фоновую графику. Controls в
  документ не попадают.
- Excel `Dilution` содержит рабочие значения и дополнительные столбцы baseline,
  факта и статуса. Листы `Округление` и `Группы H₂O` содержат параметры, итог и
  трассировку. Старый export без оптимизации сохраняет прежний формат.

## Что утверждает лаборатория

5% — предложенное начальное значение, не норматив и не доказательство
пригодности методики. Лаборатория утверждает допустимый диапазон концентраций,
диапазоны и точность дозаторов, шаги дозирования, доступный материал и резерв.
Можно задать более строгий допуск, например 2% или меньше. Пресеты 1/5/10 мкл
служат планированию и сами по себе не подтверждают точность оборудования.

Рукописные округления из примера проверяются математически, а не принимаются
за эталон. Если числовой допуск или объёмные ограничения не выполняются,
сотрудник видит статус проверки и причину.

## Файлы и проверки

- `backend/app/services/protocol_dilution_optimizer.py`: чистый batch optimizer.
- `backend/app/services/protocols.py`: фаза после baseline, preview/snapshot.
- `backend/app/schemas/protocols.py`: настройки и ограничения API.
- `backend/app/services/protocol_excel.py`: рабочий export и аудит.
- `frontend/src/api/types.ts`: typed настройки, metadata и группы.
- `frontend/src/pages/ProtocolsCreatePage.tsx`: payload, hydration, свежий preview.
- `frontend/src/components/protocols/ProtocolDilutionOptions.tsx`: controls и группы.
- `frontend/src/components/protocols/ProtocolSheet.tsx`: интеграция блока.
- `frontend/src/components/protocols/ProtocolSupplementTables.tsx`: tooltip, сортировка, аудит.
- `frontend/src/components/protocols/ProtocolPrintDocument.tsx`: выбранные печатные разделы без аудита округления.
- `frontend/src/styles/app.css`: компактное отображение и печатные стили.

Backend tests проверяют примеры концентраций, оба направления, две ступени,
несовместимые ограничения, baseline вне допуска, сохранение ID/лунок,
детерминизм, производительность 300/2000 строк, snapshot и совпадение XLSX.
Playwright проверяет controls, группировку, совместимость с минимумом 15 мкл,
сохранение/открытие, равенство экранных и печатных значений, отдельную печать
разведений, исключение аудита, пустой выбор и заливку строк в print media.
PDF формируется с отключённой фоновой графикой. Данные нового сценария
подаются через API-моки. Существующий smoke использует текущий backend.
