# Описание проекта: лабораторный ДНК-реестр

Этот документ описывает, как устроен проект лабораторного ДНК-реестра и по какому принципу он работает. `README.md` остается короткой практической инструкцией по запуску и проверкам, а этот файл служит общей картой системы для пользователя, администратора и разработчика.

## 1. Назначение проекта

Сервис заменяет ручную работу с большими Excel-реестрами лаборатории. Главная идея:

- Excel используется как формат импорта и экспорта.
- PostgreSQL является основным источником данных.
- Пользователь работает не с отдельными файлами, а с партиями, объектами, этапами работ, историей попыток и справочниками.

Базовая модель предметной области:

```text
партии -> объекты -> повторяемые этапы -> исполнители -> история / аудит
```

В интерфейсе партия воспринимается как рабочая таблица. Этап работы воспринимается как набор колонок этой таблицы. Повторы этапа сохраняются в истории, а в основной таблице показывается последняя актуальная попытка.

## 2. Архитектура

Проект состоит из нескольких частей:

- Frontend: React, Vite, TypeScript.
- Backend: FastAPI, SQLAlchemy async.
- Database: PostgreSQL.
- Migrations: Alembic.
- Excel/табличный импорт: `python-calamine`.
- Excel-экспорт: `openpyxl`.
- Dev/prod запуск: Docker Compose.
- Внешний пользовательский порт: `4001`.

При обычном запуске:

```bash
docker compose up -d --build
```

пользователь открывает приложение по адресу:

```text
http://localhost:4001
```

Снаружи публикуется frontend/nginx. Backend остается внутренним compose-сервисом и доступен из браузера через `/api`.

## 3. Основные пользовательские разделы

### Главная

Показывает общую сводку по базе: партии, объекты, состояние этапов и быстрые переходы.

### Партии

Главный рабочий экран. Слева находится список партий, справа - таблица выбранной партии.

Внутри партии есть вкладки:

- `Регистрация`;
- `Пробоподготовка`;
- `Измельчение`;
- `Выделение`;
- `RealTime`;
- `ПЦР`;
- `Электрофорез`;
- `Анализ`;
- `Все этапы`.

Каждая вкладка показывает свой набор колонок. На этапах отображается последняя актуальная попытка, а повторы остаются доступными как история.

### Объекты

Общий список объектов с поиском и фильтрацией. Объект можно открыть в карточке.

### Карточка объекта

Вторичный экран для подробного просмотра одного объекта. Карточка показывает регистрационные данные, timeline, этапы, RT-результаты и историю.

### Массовое заполнение

Экран для внесения данных этапа сразу по группе объектов. Пользователь выбирает этап, партии/объекты, заполняет поля, смотрит preview и применяет изменения.

Массовое заполнение не затирает старые данные этапа. Оно создает новую попытку.

### Поиск

Ищет по объектам, партиям, номерам, следователям, типам объектов, исполнителям, методам, этапам, RT-результатам и другим сохраненным данным.

### Отчёты

Управленческий раздел для руководителя лаборатории. Он собирает данные из партий, объектов, `stage_events`, исполнителей и контрольных полей партии.

В первой версии доступны:

- `Обзор` - KPI по партиям, объектам, незавершённым этапам, повторным этапам и проблемным признакам;
- `Контроль партии` - отдельный отчёт по контрольным полям с вычисляемым статусом контроля и экспортом в Excel;
- `Ход работы` - готовность партий по лабораторным этапам, отстающий этап и быстрые фильтры;
- `Статистика` - агрегаты по неделям, месяцам и годам.

Фильтры отчётов сохраняются в URL и учитывают годовой контекст `case_year`, партии, период, этап, исполнителя, тип объекта, коробку, архивные и пустые партии.

### Справочники

Содержит сотрудников и лабораторные значения:

- сотрудники;
- роли сотрудников;
- привязки сотрудников к этапам;
- реактивы и значения для выпадающих списков;
- методы выделения;
- методы RealTime;
- панели ПЦР;
- секвенаторы;
- статусы анализа.

### Импорт реестра

Загрузка одного или нескольких Excel-файлов реестра. Перед записью в базу всегда делается preview.

### Импорт RT

Загрузка файлов RT/qPCR: `.xls`, `.xlsx`, `.csv`. Поддерживается универсальная таблица и ABI/QuantStudio-подобные файлы.

### Экспорт

Формирует Excel-файл в старом формате реестра, но данные берет из PostgreSQL и актуальных stage-событий.

## 4. Жизненный цикл данных

Типовой путь данных выглядит так:

```text
Excel-файл
  -> preview импорта
  -> commit импорта
  -> партия
  -> объекты
  -> stage_events и detail-таблицы
  -> таблицы интерфейса / поиск / экспорт
```

Preview нужен, чтобы пользователь увидел:

- номер партии;
- количество найденных объектов;
- новые и существующие объекты;
- найденные этапы;
- пропущенные строки;
- предупреждения;
- дубликаты.

Commit записывает данные в PostgreSQL. Исходные значения Excel сохраняются в `raw_registry_json` у объекта и в `raw_json` у событий этапов. Это нужно, чтобы можно было понять, откуда пришли данные и как они выглядели в исходном файле.

## 5. Партии

Партия - это верхний рабочий контейнер для группы объектов. Номер партии берется из имени Excel-файла, например:

- `№ 148 реестр.xlsx`;
- `143 партия.xlsx`;
- `партия 143.xlsx`.

В таблице `parties` хранятся:

- номер партии;
- статус;
- комментарий;
- количество объектов;
- контрольные строки из Excel;
- служебные raw-данные.

Архивирование партии не удаляет объекты физически. Архивная партия скрывается из обычного списка, но может быть показана через режим просмотра архивных.

## 6. Объекты

Объект - это строка лабораторного реестра. Основная таблица: `objects`.

В объекте хранятся:

- номер `№ рег РЦСМЭ`;
- номер постановления;
- номер партии;
- дата поступления;
- дата постановления;
- следователь;
- номер в/ч;
- тип объекта;
- коробка;
- количество пакетов;
- описание;
- исходная строка импорта в `raw_registry_json`.

Для списков используется облегченная выдача без тяжелых raw-полей. Полная raw-информация нужна в карточке объекта, импорте, истории и диагностике.

## 7. Повторяемые этапы

Основная таблица этапов - `stage_events`.

Каждое событие этапа содержит:

- объект;
- тип этапа;
- номер попытки `attempt_no`;
- дату события;
- источник;
- комментарий;
- raw-данные;
- флаг отмены;
- связь с рабочей сессией;
- исполнителей.

Типы этапов:

- `sample_prep` - пробоподготовка;
- `milling` - измельчение;
- `dna_extraction` - выделение;
- `realtime` - RealTime / концентрация;
- `pcr` - ПЦР;
- `electrophoresis` - электрофорез;
- `analysis` - анализ.

Для пользователя этап `dna_extraction` отображается как `Выделение`.

### Принцип повторов

Старые попытки не перезаписываются. Если пользователь вручную меняет этап или делает массовое заполнение, система создает новую попытку. В таблице партии показывается последняя актуальная попытка, а история остается доступной.

Если событие отменяется, оно помечается `is_cancelled=true`, а не удаляется физически.

## 8. Detail-таблицы этапов

Общие поля этапа лежат в `stage_events`, а специфичные поля каждого этапа лежат в detail-таблицах:

- `sample_prep_details` - пробоподготовка;
- `milling_details` - измельчение и стаканы;
- `dna_extraction_details` - выделение;
- `realtime_details` - метод, концентрация, Ct/Cq, DI, IPC;
- `pcr_details` - ПЦР;
- `electrophoresis_details` - электрофорез;
- `analysis_details` - генотип и статус анализа.

Такой подход позволяет хранить все этапы одинаково с точки зрения истории, но не смешивать специфичные поля разных лабораторных операций.

## 9. Рабочие сессии и массовое заполнение

Рабочая сессия хранится в `work_sessions`. Она связывает:

- этап;
- выбранную партию или набор объектов;
- дату работы;
- автора;
- источник;
- статус;
- созданные события этапов.

Связь объектов с сессией хранится в `work_session_objects`.

Массовое заполнение всегда проходит через preview. Preview показывает, сколько объектов будет затронуто и какие попытки будут созданы. Apply создает новые `stage_events`.

## 10. Источники данных

У stage-событий и связанных сущностей есть источник:

- `registry_excel` - импортировано из Excel-реестра;
- `manual` - внесено вручную или через массовое заполнение;
- `rt_import` - импортировано из RT/qPCR-файла.

При повторном импорте Excel сервис обновляет импортированные из Excel данные, но не должен уничтожать ручную историю пользователя.

## 11. Импорт реестра

Импорт реестра работает по листу `список объектов`.

Импортер:

- не доверяет Excel `usedRange` как источнику истины;
- определяет реальные строки по объектоподобным значениям;
- пропускает служебные строки;
- нормализует даты, номера и пробелы;
- извлекает номер партии из имени файла;
- сохраняет исходные значения;
- создает или обновляет партию;
- создает или обновляет объекты;
- переносит заполненные лабораторные этапы в canonical-модель.

Если объект уже есть по `№ рег РЦСМЭ` или `№ постановления`, сервис не создает дубль объекта, а обновляет регистрационные данные и этапы.

## 12. Импорт RT/qPCR

RT/qPCR-импорт хранится отдельно:

- запуск RT - `rt_runs`;
- результаты - `rt_results`.

Сервис пытается сопоставить строки RT с объектами по номерам и числовой основе. Несопоставленные результаты остаются в базе как результаты без объекта, чтобы их можно было разобрать позже.

## 13. Справочники

Справочники нужны, чтобы интерфейс не заставлял каждый раз вводить одинаковые значения руками.

### Сотрудники

Таблица `employees` хранит:

- ФИО;
- краткое имя;
- инициалы;
- роль;
- активность;
- признак подтверждения.

Связь сотрудника с этапами хранится в `employee_stage_roles`. Это позволяет показывать в выпадающих списках меньше лишних ФИО.

### Значения и реактивы

Таблица `reference_items` хранит универсальные значения по категориям:

- реактивы;
- методы выделения;
- методы RealTime;
- панели ПЦР;
- секвенаторы;
- методы пипетирования;
- статусы анализа.

При импорте Excel новые найденные значения могут добавляться в справочник, чтобы потом их можно было выбрать из списка.

## 14. Пользователи и роли

В системе есть роли:

- `admin` - полный доступ, включая администрирование и архивирование;
- `user` - рабочий пользователь, может импортировать и редактировать разрешенные данные;
- `viewer` - только просмотр.

Авторизация локальная. Сессия хранится через httpOnly cookie.

В dev-сборке создаются тестовые логины:

- `admin / admin123`;
- `user / user123`;
- `viewer / viewer123`.

## 15. Аудит и история

Важные изменения пишутся в `audit_log`. Аудит нужен, чтобы видеть:

- кто изменил данные;
- какую сущность изменили;
- какое действие было выполнено;
- состояние до и после изменения.

История лабораторных этапов хранится не только в аудите. Основная история этапов - это сами повторные `stage_events`.

## 16. Экспорт

Экспорт создает Excel-файл, совместимый со старым реестром.

Принцип экспорта:

- регистрационные поля берутся из `objects`;
- лабораторные поля берутся из последних актуальных `stage_events`;
- исходные raw-значения используются там, где это помогает сохранить старый формат;
- при избытке повторов история может выгружаться отдельными листами.

Excel остается форматом обмена с внешним миром, но не основным хранилищем.

## 17. Хранение файлов

Оригиналы импортированных файлов сохраняются в volume `/app/data`. Файлы привязываются к import batch и хранятся по SHA256, чтобы можно было диагностировать повторные импорты и происхождение данных.

Docker volumes:

- `postgres_data` - данные PostgreSQL;
- `storage` - загруженные файлы и служебное файловое хранилище.

## 18. API

Все основные backend-маршруты начинаются с `/api`.

Основные группы:

- `/api/auth` - вход, выход, текущий пользователь;
- `/api/dashboard` - сводка;
- `/api/parties` - партии, объекты партии, прогресс;
- `/api/objects` - объекты и карточка объекта;
- `/api/parties/{id}/stage-table/...` - табличные данные этапов;
- `/api/stage-events/...` - preview/apply этапов;
- `/api/work-sessions` - рабочие сессии;
- `/api/employees` - сотрудники;
- `/api/reference-items` - справочники значений;
- `/api/imports/registry` - импорт реестров;
- `/api/imports/rt` - импорт RT/qPCR;
- `/api/exports` - Excel-экспорт;
- `/api/audit` - аудит.

Frontend-клиент для этих endpoints находится в `frontend/src/api/client.ts`.

## 19. Как читать код

Основные папки:

- `backend/app/api` - FastAPI endpoints, авторизация доступа и HTTP-контракты;
- `backend/app/services` - бизнес-логика: импорт, этапы, экспорт, аудит, авторизация;
- `backend/app/parsers` - чтение Excel/CSV и нормализация входных файлов;
- `backend/app/models` - SQLAlchemy модели базы данных;
- `backend/app/schemas` - Pydantic-схемы API;
- `frontend/src/pages` - основные экраны интерфейса;
- `frontend/src/components` - общие UI-компоненты;
- `frontend/src/api` - frontend-клиент API и TypeScript-типы;
- `frontend/src/styles` - CSS интерфейса;
- `alembic/versions` - миграции базы данных;
- `docker` - nginx и Docker-конфигурация.

Если нужно понять конкретную функцию:

1. Найти экран в `frontend/src/pages`.
2. Посмотреть, какой метод вызывается из `frontend/src/api/client.ts`.
3. Найти соответствующий endpoint в `backend/app/api`.
4. Перейти в сервис из `backend/app/services`.
5. Проверить модели в `backend/app/models/entities.py`.

## 20. Эксплуатация и проверки

Запуск:

```bash
docker compose up -d --build
```

Открыть:

```text
http://localhost:4001
```

Smoke-проверка:

```bash
curl http://localhost:4001/
```

Backend-тесты:

```bash
APP_PORT=4001 docker compose run --rm \
  -e PYTHONPATH=/app \
  -v /home/drcramer/dna_base/backend/tests:/app/tests \
  -v /home/drcramer/.codex/attachments:/home/drcramer/.codex/attachments:ro \
  backend pytest tests
```

Frontend-сборка:

```bash
cd frontend
npm run build
```

Backup базы:

```bash
docker compose exec postgres pg_dump -U dna -d dna_registry > backup.sql
```

Backup файлового хранилища:

```bash
docker run --rm -v dna_base_storage:/data -v "$PWD":/backup alpine \
  tar czf /backup/storage-backup.tgz -C /data .
```

## 21. Главные принципы проекта

- Не терять историю: новые этапы создают новые попытки.
- Не доверять Excel как базе данных: Excel только входной/выходной формат.
- Показывать preview перед массовыми изменениями.
- Хранить исходные raw-значения для диагностики.
- Не удалять важные данные физически без необходимости: архивирование и отмена предпочтительнее удаления.
- Делать интерфейс похожим на рабочую лабораторную таблицу, а не на CRM-карточки.
